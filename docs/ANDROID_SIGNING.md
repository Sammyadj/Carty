# Android Release signing

Release builds require an explicitly configured upload keystore. Carty no longer
falls back to Android's debug signing key. Debug builds remain available without
release credentials. This follows [Flutter's Android signing setup](https://docs.flutter.dev/deployment/android#sign-the-app).

## Owner setup

If an Android version has already been distributed, use the correct existing
upload identity; do not casually replace it. This change creates no production
key and does not enrol or upload anything to Google Play.

Create/select the upload key in Android Studio using **Build → Generate Signed
Bundle / APK**, or follow the linked Flutter instructions. Keep its keystore,
passwords and recovery backup outside the repository. Do not send them in chat.

Copy `android/key.properties.example` to `android/key.properties` and replace
the four placeholders locally. `storeFile` can be an absolute path or a path
relative to `android/`. The real properties file and `*.jks`/`*.keystore` files
are ignored by Git. A path outside the repository is recommended for the key.

CI may supply these instead. Each environment value overrides its matching
file property; empty environment values are treated as missing configuration.

| Property | Environment variable |
| --- | --- |
| `storeFile` | `CARTY_ANDROID_STORE_FILE` |
| `storePassword` | `CARTY_ANDROID_STORE_PASSWORD` |
| `keyAlias` | `CARTY_ANDROID_KEY_ALIAS` |
| `keyPassword` | `CARTY_ANDROID_KEY_PASSWORD` |

Use the CI secret store for passwords and materialise a keystore only on the
private runner. Avoid shell tracing and printing credentials. No credentials
are read by or compiled into Dart.

## Build and verify

From the project root:

```sh
flutter build appbundle --release
```

For a local Android APK test, use `flutter run --release -d <android-device-id>`
after configuring signing. Release tasks fail early with a configuration message
if any input or the keystore file is missing. AGP then validates the passwords
and alias against the actual key; merely passing the configuration check does
not establish that the credentials work.

Debug development still uses `flutter run -d <android-device-id>` without this
setup. iPhone signing and the Release app installed on Panda are unaffected.

Before uploading, verify the actual signed artifact's certificate and upload
key against the intended Google Play app. An APK can be inspected with the
Android SDK's `apksigner verify --verbose --print-certs <apk>`; bundles can be
checked with `jarsigner -verify <aab>`. Test keys used by automated/native checks
are disposable verification fixtures and must never be uploaded as app releases.

## Regression verification

`tool/verify_android_signing.py` invokes real native builds. It checks missing
and incomplete configuration, an absent keystore, a successful Debug build with
no signing inputs, and a successful Release APK signed by a temporary key. It
then checks the APK certificate against that key and removes both the fixture
and test-signed APK. Run in a checkout without private `android/key.properties`:

```sh
python3 tool/verify_android_signing.py \
  --gradle android/gradlew \
  --apksigner /path/to/android-sdk/build-tools/version/apksigner
```

The Gradle wrapper is generated by Flutter's Android build tooling if absent.
Use Java 21 as configured in CI. The Android signing workflow runs this check
for signing/dependency changes using a disposable key; it does not need or
publish production secrets or artifacts.
